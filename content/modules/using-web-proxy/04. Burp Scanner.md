title: Burp Scanner
---

Burp's automated vulnerability scanner. Crawls the target, runs passive checks on observed traffic, then actively fuzzes insertion points for known vuln classes (SQLi, XSS, SSRF, OS command injection, path traversal, deserialization, and many more). It's the strongest commercial web scanner in the field.

> [!warning] Pro-only feature
> Scanner is not included in Burp Community. If you don't have a Pro license, jump to [[05. ZAP Scanner|ZAP Scanner]].

## Three Ways to Start a Scan

1. **From Proxy History** — right-click a request → `Scan` (configure) or `Passive/Active scan` (quick-start)
2. **New Scan button** on the Dashboard — scan from scratch against a URL list
3. **From scope** — scan everything in Target Scope at once

## Target Scope

Before launching a scan, define what's in and out. Scope controls not just the scanner but every Burp feature if you enable `restrict to in-scope`.

Add items:
- `Target > Site map` → right-click target → `Add to scope`
- Or `Target > Scope` → `Include in scope` → `Add`

Exclusions matter as much as inclusions. Add these paths to `Exclude from scope`:
- `/logout`, `/signout`
- `/password/reset`
- `/admin/delete/*`
- Anything that mutates state destructively

> [!warning] Scope is also damage control
> An Active Scan without proper exclusions will log you out mid-scan, delete your test data, or trigger rate-limiting. Spend 60 seconds on exclusions before clicking Start.

For complex scopes (multi-host, regex paths) enable `Use advanced scope control`.

## Crawler

A web crawler builds a map of the target by following every link, form, and JS-exposed endpoint. The output lands in `Target > Site map`.

New Scan → pick `Crawl` (no vuln testing) or `Crawl and Audit` (crawl then scan).

> [!note] The crawler doesn't fuzz for hidden content
> Burp's crawler only follows links it can see. Unreferenced directories like `/admin/` won't appear unless you link-feed them from another tool. Run `ffuf` or Burp Intruder for content discovery, then add findings to scope, then re-crawl.

### Crawl Configuration

`Scan configuration` tab → `Select from library` for presets:
- `Crawl strategy - fastest` — quick, superficial
- `Crawl strategy - most complete` — slow, thorough
- `Crawl limit - 10 minutes` — bounded by time
- `Crawl limit - 30 minutes`

Click `New` for a custom config to tune crawl depth, link limits, form submission behavior, etc.

### Application Login

`Application login` tab lets you:
- Supply credentials (Burp tries them against detected login forms)
- Record a manual login via the pre-configured browser — Burp replays those steps to maintain session during the scan

Auth matters — the crawler can't see the admin area without a session. Always scan authenticated if you have creds.

## Passive Scanner

Analyzes traffic that's already flowed through Burp. No new requests sent. Looks for:
- Missing security headers (HSTS, X-Frame-Options, CSP)
- Cookie flags (HttpOnly, Secure, SameSite)
- Information disclosure (version strings, stack traces, comments)
- Potential DOM-based XSS from static JS analysis
- Mixed content, insecure form submissions

Start it with right-click → `Do passive scan` or `Passively scan this target`.

Findings land in `Dashboard > Issue activity` and `Target > Issues`.

> [!tip] Passive scans are safe to run everywhere
> No requests sent = no risk of breaking the app or triggering WAF. Run passive on every captured request as a baseline.

## Active Scanner

The main event. Sends payloads to identified insertion points to prove vulnerabilities exist.

Workflow:
1. Crawls / uses existing site map to find insertion points
2. Runs passive checks on all pages
3. Actively fuzzes parameters, headers, cookies, URL paths, JSON/XML bodies with payloads for each vuln class
4. Verifies passive-scan findings by sending confirmation payloads
5. Runs JS analysis for client-side issues

### Audit Configuration

`Audit configuration` tab → `Select from library`:
- `Audit checks - all` — full coverage, slow
- `Audit checks - critical issues only` — focuses on RCE, SQLi, SSRF, deserialization
- `Audit checks - passive` — no payloads sent
- `Audit checks - light active` — balanced
- `Audit checks - medium active` — more coverage
- `Audit checks - thorough` — exhaustive

Pick based on time budget and engagement rules of engagement. `critical issues only` is a good default for "find me RCE in 1 hour".

You can also narrow insertion point types (URL params, body, cookies, headers, URL file extension, etc.) to speed things up.

### Watching the Scan

Dashboard → Tasks → `View details` → `Logger` tab shows every request. Useful for debugging false negatives or seeing if the scanner's getting blocked.

Big scans run for hours. Keep Burp open and don't block on finishing.

## Issue Activity

Dashboard shows all discovered issues with:
- **Severity**: High, Medium, Low, Information
- **Confidence**: Certain, Firm, Tentative

> [!tip] Triage by Severity + Confidence
> `High + Certain/Firm` → verify and exploit now. `High + Tentative` → manual verification — often false positives but worth checking. `Medium` and below → batch for the report. Never trust tool output without reproducing manually.

Click any issue for:
- Advisory text (what it is, impact, remediation)
- The exact request Burp sent to prove it
- The response showing the vulnerability

Send the proof request to Repeater (`CTRL+R`) to replay and exploit.

## Reporting

`Target > Site map` → right-click target → `Issue > Report issues for this host`. Pick HTML or XML output, choose severity filter, include/exclude request/response data.

> [!warning] Tool reports are appendix data, never deliverables
> Dump the raw Burp report into an appendix if the client wants it. Your actual report is written by you, with your own analysis, chains, and business-impact mapping. Handing a client a Burp HTML and calling it a pentest report is how you lose repeat work.
