Brute forcing a login is the last-resort credential attack — loud, slow, and easy to detect. Done wrong, it locks out every account in the domain and gets your IP banned. Done right, it finds the one admin who still uses `Winter2024!`.

## Attack Modes

- **Brute force** — every combination in a charset. Only viable for very short passwords or when you know the format (e.g. 6-digit PIN).
- **Dictionary** — a wordlist of known or likely passwords (rockyou, leaked dumps, vendor defaults). The default approach.
- **Hybrid** — dictionary words mutated with rules (append year, leetspeak, capitalise). hashcat rules are the standard way to expand small lists into big ones without exploding entropy.
- **Password spraying** — one password tried against many users. Beats account lockouts because no single account hits the threshold.
- **Credential stuffing** — leaked `user:pass` pairs replayed against the target. Relies on password reuse.

## Picking the Right Mode

| Situation | Mode |
| --- | --- |
| Domain account with lockout policy | Spray |
| Single service, no lockout (SSH on VPS) | Dictionary + rules |
| Known password format (e.g. `[A-Z]{1}[a-z]{5}[0-9]{2}`) | Brute with mask |
| Known leak tied to users | Credential stuffing |
| Internal corp target | Season+Year spray (`Spring2025!`, `Autumn2025`) |

## Target Selection

Not every login screen is worth attacking. Rank candidates by:

1. **Lockout policy** — no lockout = free attempts. Test with one throwaway user and three wrong passwords; if the account still authenticates on a known-good password, you're clear.
2. **Rate limiting** — a 429 after 5 attempts tells you to slow down or move on.
3. **MFA / CAPTCHA** — a brute won't beat these. Look for a non-MFA endpoint (legacy API, mobile backend, SMTP/IMAP) that authenticates the same credentials.
4. **Error message granularity** — "invalid username or password" is worse for you than "invalid password" (which confirms the user exists). Enumerate first on the chatty endpoint, brute on the strict one.

## Lockouts and Rate Limits

> [!warning] Lockouts are an engagement-killer
> Locking out hundreds of domain accounts triggers SOC alerts, pages help-desk staff, and ends your access. Always confirm lockout threshold before brute-forcing — and when in doubt, spray.

Rough rules of thumb:

- AD default lockout: 5 bad attempts in 30 min, 30 min lockout
- Spray at most **2-3 passwords per account per lockout window**
- Pause between spray rounds (sleep for the lockout window + buffer)
- For rate-limited HTTP endpoints, drop to `-t 1` and add a wait (`-W`)

## Noise

Brute forcing writes to every auth log on the target. Assume:

- SSH: `/var/log/auth.log` or `/var/log/secure`, one line per attempt
- Windows: Event ID 4625 per failed logon, 4740 on lockout
- Web: access logs + WAF alerts

If stealth matters more than coverage, narrow the wordlist to a dozen high-probability candidates instead of a 14-million-line dump.

> [!tip] Always enumerate before you brute
> Every valid username you confirm beforehand cuts the attack space massively. Start with [[02. Custom Wordlists|username enumeration]] — SMB null sessions, LDAP, OSINT, error-message oracles — before loading hydra.

## When Brute Forcing Is The Wrong Answer

- The target has MFA on every surface → find a credential-leak path instead
- You've got a valid session cookie → ride the session, don't re-login
- The password hash is dumpable → crack offline, no network noise
- A SSRF or SQLi gives direct DB access → read the users table
