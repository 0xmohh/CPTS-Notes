---
title: Parameter Fuzzing
---

Hidden parameters are one of the highest-value finds in a web assessment. Developers leave debug flags, admin toggles, and legacy inputs wired up long after the UI stops referencing them — and they rarely get the same validation the public parameters get. Ffuf is the right tool for finding them.

## GET Parameter Names

Place `FUZZ` as the parameter name after the `?`:

```bash
ffuf -w /opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ \
     -u 'http://target.htb/admin.php?FUZZ=key'
```

> [!warning] You'll get 200 OK on every request
> The page loads fine whether the parameter exists or not. The only difference is often the response size — the app includes extra output when a real parameter triggers a code path. Baseline the no-param response and filter by size.

```bash
# baseline
curl -s 'http://target.htb/admin.php?x=1' | wc -c
# 1234

ffuf -w burp-parameter-names.txt:FUZZ \
     -u 'http://target.htb/admin.php?FUZZ=key' \
     -fs 1234
```

Anything hitting a different size is reaching a different code path — a real parameter.

### Parameter wordlists

```
Discovery/Web-Content/burp-parameter-names.txt         Burp's extensive list
Discovery/Web-Content/api/api-endpoints.txt            API-style parameters
Discovery/Web-Content/api/objects.txt                  object/resource names
```

## POST Parameter Names

POST bodies aren't in the URL — move `FUZZ` into the `-d` body and set the right `Content-Type`:

```bash
ffuf -w /opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ \
     -u http://target.htb/admin.php \
     -X POST \
     -d 'FUZZ=key' \
     -H 'Content-Type: application/x-www-form-urlencoded' \
     -fs 1234
```

> [!tip] Content-Type matters
> PHP's `$_POST` only populates when the request has `Content-Type: application/x-www-form-urlencoded` (or `multipart/form-data`). Without that header, the body is ignored entirely and every parameter looks dead. Set the header explicitly.

For JSON APIs:

```bash
ffuf -w burp-parameter-names.txt:FUZZ \
     -u http://target.htb/api/user \
     -X POST \
     -d '{"FUZZ":"key"}' \
     -H 'Content-Type: application/json'
```

## Confirming a Hit

Once ffuf flags a parameter name — say `id` — hit it manually and read the response:

```bash
curl http://target.htb/admin.php \
     -X POST \
     -d 'id=key' \
     -H 'Content-Type: application/x-www-form-urlencoded'

<div class='center'><p>Invalid id!</p></div>
```

That error is confirmation: the parameter exists, the app reads it, and now the test moves to what valid values look like.

## Value Fuzzing

Once you know the parameter name, fuzz the value:

```bash
# generate a simple numeric wordlist
seq 1 1000 > ids.txt

ffuf -w ids.txt:FUZZ \
     -u http://target.htb/admin.php \
     -X POST \
     -d 'id=FUZZ' \
     -H 'Content-Type: application/x-www-form-urlencoded' \
     -fs 1234
```

Match the wordlist to the expected value type:

- Numeric IDs — `seq 1 10000`, or short ID lists
- Usernames — `SecLists/Usernames/`
- Filenames — `SecLists/Fuzzing/LFI/LFI-Jhaddix.txt` for LFI testing
- UUIDs — generally not brute-forceable, but worth noting shape
- Tokens — rarely brute-forceable; look for leaks instead

### LFI value fuzzing

A parameter that accepts filenames is a prime LFI candidate:

```bash
ffuf -w /opt/useful/seclists/Fuzzing/LFI/LFI-Jhaddix.txt:FUZZ \
     -u 'http://target.htb/index.php?file=FUZZ' \
     -fs 1234
```

Baseline the default response, then any size difference is either a successful file read or a different error path — both worth looking at.

## Fuzzing Multiple Parameters

You can `FUZZ` both the name and a candidate value at once with multiple keywords (see [[05. Advanced Techniques|Advanced Techniques]]):

```bash
ffuf -w param-names.txt:PARAM -w values.txt:VALUE \
     -u 'http://target.htb/admin.php?PARAM=VALUE' \
     -mode clusterbomb \
     -fs 1234
```

> [!note] GET first, then POST
> GET parameter discovery is cheaper and less intrusive. Run it first. If the endpoint accepts POST, repeat the scan over POST — endpoints often accept both and expose different parameters per method.
