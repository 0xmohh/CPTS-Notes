Ffuf has two flags you'll use every single time: `-w` for the wordlist and `-u` for the target URL. The keyword `FUZZ` tells ffuf where in the request to substitute each line of the wordlist.

## The FUZZ Keyword

The classic form:

```bash
ffuf -w /opt/useful/seclists/Discovery/Web-Content/common.txt:FUZZ \
     -u http://target.htb/FUZZ
```

Ffuf walks the wordlist and sends one request per line, replacing `FUZZ` in the URL. The keyword name isn't magic — `-w list.txt:PANDA` works the same if you put `PANDA` in your URL. Stick with `FUZZ` out of habit, and keep multiple keywords unique when you need more than one.

> [!tip] Bind keyword to wordlist explicitly
> Always use the `wordlist.txt:FUZZ` form rather than relying on default behavior. It's required as soon as you have more than one wordlist and it makes your commands readable.

## Reading the Output

A typical result line looks like this:

```
admin                   [Status: 301, Size: 310, Words: 20, Lines: 10]
```

Four signals matter:

- **Status** — HTTP response code
- **Size** — response body length in bytes
- **Words** — whitespace-separated token count
- **Lines** — newline count

Any one of these can be the fingerprint of a real find versus a generic 404 page.

## Matchers vs Filters

Ffuf shows a response if it matches the matchers AND doesn't match the filters.

Matchers (keep):

```
-mc 200,301,403         match status codes
-ms 1234                match exact size
-mw 42                  match word count
-ml 10                  match line count
-mr "admin|secret"      match regex in body
```

Filters (drop):

```
-fc 404,500             filter status codes
-fs 0                   filter size zero
-fw 200                 filter word count
-fl 50                  filter line count
-fr "Not Found"         filter regex in body
```

By default, ffuf matches `200,204,301,302,307,401,403` and filters nothing. You'll usually need to tighten that for noisy targets.

## When Everything Returns 200

A common trap: the application returns a 200 OK with a generic "page not found" body for every unknown path. Every line of your wordlist becomes a false positive.

The fix is filtering by response characteristics instead of status code:

```bash
ffuf -w common.txt:FUZZ -u http://target.htb/FUZZ -fs 1256
```

Send one request to a path you know doesn't exist (`/thisdefinitelydoesnotexist`) and record its size. That number is your `-fs` value. Any real page will differ in size and slip past the filter.

> [!note] Baseline before you fuzz
> `curl -s http://target.htb/does-not-exist | wc -c` gives you the baseline size in one line. Do this before every content-discovery scan.

## Common Flags You'll Use

```
-t 40                threads (default)
-p 0.1               delay in seconds between requests
-rate 50             requests per second cap
-timeout 10          per-request timeout
-r                   follow redirects
-v                   verbose — shows full URL per hit
-c                   colorized output
-s                   silent — print only results
-o out.json -of json save output
```

> [!warning] Follow redirects can hide results
> `-r` is convenient but merges 301/302 responses into their destination. If you're specifically looking for redirects (common for admin panels), leave `-r` off and read the `Location` headers.

## A Complete First Command

Put it together:

```bash
ffuf -w /opt/useful/seclists/Discovery/Web-Content/common.txt:FUZZ \
     -u http://target.htb/FUZZ \
     -mc 200,204,301,302,307,401,403 \
     -fs 0 \
     -c -v
```

From here, every other technique in this module is a variation: move the `FUZZ` keyword, change the wordlist, add filters, layer more keywords. The mental model stays the same.
