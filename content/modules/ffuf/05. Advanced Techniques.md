title: Advanced Techniques
---

Once you're comfortable with single-keyword fuzzing, ffuf's real power opens up: multiple fuzz positions, authenticated scans, config files, and surgical filtering. These are the techniques that turn ffuf from a content-discovery tool into a general-purpose request fuzzer.

## Multiple FUZZ Keywords

Bind each wordlist to a distinct keyword:

```bash
ffuf -w users.txt:USER -w passwords.txt:PASS \
     -u http://target.htb/login.php \
     -X POST \
     -d 'username=USER&password=PASS' \
     -H 'Content-Type: application/x-www-form-urlencoded' \
     -mode clusterbomb \
     -fs 1234
```

The `-mode` flag controls how ffuf pairs the wordlists:

- **`clusterbomb`** (default when multiple wordlists) — every combination of every wordlist. 100 users × 100 passwords = 10,000 requests
- **`pitchfork`** — parallel iteration: line 1 of each wordlist together, line 2 together, and so on. Wordlists must be the same length
- **`sniper`** — one keyword per request, cycles through each position

### Example — pitchfork for credential lists

When you have paired `user:pass` dumps split into two files:

```bash
ffuf -w users.txt:USER -w passwords.txt:PASS \
     -u http://target.htb/login.php -X POST \
     -d 'username=USER&password=PASS' \
     -H 'Content-Type: application/x-www-form-urlencoded' \
     -mode pitchfork \
     -fc 401
```

## Authenticated Fuzzing

Most interesting attack surface is behind a login. Use `-b` for cookies or `-H` for tokens:

```bash
# cookie session
ffuf -w raft-small-words.txt:FUZZ \
     -u http://target.htb/admin/FUZZ \
     -b 'PHPSESSID=abc123; auth=admin' \
     -e .php

# bearer token
ffuf -w api-endpoints.txt:FUZZ \
     -u http://target.htb/api/v1/FUZZ \
     -H 'Authorization: Bearer eyJhbGc...'
```

> [!warning] Sessions expire mid-scan
> If your scan starts returning 302 redirects to `/login.php` partway through, the session died. Grab a fresh cookie and resume. Longer-running scans should be split into chunks with periodic session refreshes.

## Fuzzing Headers

Headers are a legitimate `FUZZ` target — useful for finding header-based auth bypasses, user-agent gating, or hidden debug toggles:

```bash
# User-Agent fuzz
ffuf -w user-agents.txt:FUZZ -u http://target.htb/ -H 'User-Agent: FUZZ' -fs 1234

# arbitrary debug headers
ffuf -w header-names.txt:FUZZ -u http://target.htb/admin -H 'FUZZ: 1' -fc 403
```

Header-name fuzzing has caught `X-Forwarded-For`, `X-Original-URL`, `X-Rewrite-URL`, `X-Custom-IP-Authorization`, and similar bypass primitives on real engagements.

## Filtering Tricks

### Filter by regex

Match or filter on body content, not just size:

```bash
# drop anything containing "Not Found"
ffuf ... -fr 'Not Found|Page not available'

# keep only responses containing "admin" or "secret"
ffuf ... -mr 'admin|secret|api[_-]key'
```

### Range filters

Sizes can be given as ranges or comma-separated values:

```bash
-fs 0,1234          # filter size 0 or 1234
-fs 1200-1300       # filter sizes between 1200 and 1300 inclusive
```

Same for `-fw`, `-fl`, `-ms`, etc.

### Auto-calibration

Let ffuf auto-detect baseline responses and filter them out:

```bash
ffuf -w common.txt:FUZZ -u http://target.htb/FUZZ -ac
```

`-ac` sends a handful of known-bad requests first, derives the baseline response signature, and filters it automatically. Works well when you don't want to hand-tune `-fs`.

For custom calibration strings:

```bash
ffuf ... -acc 'random1' -acc 'random2'
```

## Config Files

Long ffuf commands get unwieldy. Save them to a config:

```bash
ffuf -config myscan.conf
```

The config file is a simple key/value list:

```
url = http://target.htb/FUZZ
wordlists = /opt/useful/seclists/Discovery/Web-Content/common.txt:FUZZ
extensions = .php,.html,.bak
followredirects = true
recursion = true
recursion-depth = 2
threads = 20
fs = 1234
```

Reusable across engagements and far easier to tweak than a 20-flag command line.

## Rate Control and Stealth

Default threading (`-t 40`) is fine for lab targets but will hammer production apps. Tune down:

```bash
# cap threads
ffuf ... -t 10

# randomized delay
ffuf ... -p 0.1-0.5

# requests per second cap
ffuf ... -rate 20
```

> [!tip] -rate is more useful than -t on real targets
> `-rate` is deterministic: you know exactly how many requests per second you're sending. `-t` is harder to reason about because effective rate depends on the target's response time. On client assessments, use `-rate` and agree on a number up front.

## Output for Reporting

Save machine-readable output for diffing and reporting:

```bash
ffuf ... -o scan.json -of json
ffuf ... -o scan.html -of html
ffuf ... -o scan.csv  -of csv
```

Multiple formats at once:

```bash
ffuf ... -o scan -of json,html,csv
```

## Chaining ffuf With Other Tools

Ffuf output feeds cleanly into pipelines:

```bash
# pull paths found by ffuf and feed into nuclei or sqlmap
jq -r '.results[].url' scan.json > urls.txt
nuclei -l urls.txt -t http/vulnerabilities/

# feed discovered vhosts into subsequent scans
jq -r '.results[].input.FUZZ' vhosts.json > vhosts.txt
```

## Common Pitfalls

> [!danger] Watch for false negatives
> If a scan returns zero results, don't assume the target is clean. Check: is the server rate-limiting you (connection resets)? Is your baseline filter too aggressive? Is the wordlist appropriate for the stack? Rerun with `-v` and no filters to see raw traffic before tightening.

> [!warning] -r can mask findings
> `-r` (follow redirects) hides 301/302s by resolving them. If you're looking for authentication boundaries or path-based access control, run without `-r` first.

> [!note] One attack per ffuf invocation
> Keep each ffuf run focused on one question: "what directories exist?", "what parameters exist on this endpoint?", "what Host: values are valid?". Mixing concerns makes output hard to read and filters hard to tune. Script multiple runs rather than fighting one giant command.
