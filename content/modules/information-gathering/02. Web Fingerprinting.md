---
title: Web Fingerprinting
---

Fingerprinting is identifying the technologies running behind a URL — web server, framework, CMS, language, libraries, CDN, WAF. Each identified component is a lead: a known version gets you CVE research; a known CMS gets you module-specific attacks; a known WAF tells you which bypass techniques to prepare.

## What to Identify

- **Web server** — Apache, nginx, IIS, LiteSpeed (plus version)
- **Backend language** — PHP, Node, Python, Ruby, Java, .NET
- **Framework** — Laravel, Rails, Django, Express, Spring
- **CMS** — WordPress, Drupal, Joomla, Magento
- **Front-end stack** — React, Vue, Angular, Svelte
- **CDN** — Cloudflare, Akamai, Fastly, CloudFront
- **WAF** — detected independently of CDN

## Techniques

### 1. Banner Grabbing

HTTP response headers often leak server identity:

```bash
curl -I http://TARGET
```

Example response:

```
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
X-Powered-By: PHP/7.4.3
X-Generator: WordPress 5.8
```

Three immediate findings: Apache 2.4.41 on Ubuntu, PHP 7.4.3, WordPress 5.8. Each gets a CVE search.

Modern well-configured servers strip these headers (`ServerTokens Prod` on Apache). But many don't.

### 2. HTTPS Certificate Inspection

```bash
openssl s_client -connect TARGET:443 -servername TARGET < /dev/null | openssl x509 -text
```

Certificate SANs often list every hostname on that server — a quick way to find vhosts you didn't know about.

### 3. Specific Probes

Many apps respond distinctively to specific requests:

```bash
# WordPress — leaks version in RSS, readme
curl http://TARGET/readme.html | grep -i version
curl http://TARGET/wp-login.php

# Drupal — CHANGELOG.txt often readable
curl http://TARGET/CHANGELOG.txt

# Joomla — admin panel location
curl http://TARGET/administrator

# generic 404 — often reveals framework via styling
curl http://TARGET/nonexistent-page
```

### 4. Page Content Analysis

The HTML often reveals the stack via comments, script paths, or CSS classes:

- `wp-content/` paths → WordPress
- `/sites/default/files/` → Drupal
- `csrf-token` meta tag with `X-CSRF-Token` → Laravel / Rails
- `__RequestVerificationToken` → ASP.NET
- `data-react-helmet` → React
- `ng-` attributes → Angular
- `v-` attributes → Vue

## Automated Fingerprinting Tools

### whatweb

Classic command-line fingerprinter. Signatures for hundreds of technologies.

```bash
whatweb http://TARGET

# aggressive — sends more probes, catches more things
whatweb -a 3 http://TARGET

# multiple targets
whatweb -i hosts.txt
```

### Wappalyzer

Browser extension and web service. Visual, easy to share screenshots with team members. Available as CLI too:

```bash
npx wappalyzer http://TARGET
```

### BuiltWith

Web service (builtwith.com). Historical tracking — see when a site switched from one CMS to another. Free tier is limited but often enough.

### Netcraft

```
https://sitereport.netcraft.com/?url=TARGET.com
```

Gives tech stack, hosting history, IP range — plus a security score summary.

### Nikto

Full-service web scanner. Very noisy but thorough:

```bash
nikto -h http://TARGET

# fingerprinting only (quiet)
nikto -h http://TARGET -Tuning b
```

Nikto will try 6700+ known-bad URLs and report findings. Great for initial scan; be aware it trips any WAF.

## WAF Detection

### wafw00f

```bash
wafw00f http://TARGET
```

Identifies 150+ WAFs. Example output:

```
[+] The site https://TARGET.com is behind Wordfence (Defiant) WAF.
```

Each WAF has a different bypass profile — Cloudflare is different from Imperva is different from AWS WAF. Knowing which one you're facing shapes your evasion.

### Manual WAF Detection

Three telltale signs:

- Specific response codes on bad input (403 from Cloudflare, custom branded pages from Akamai)
- Response headers like `X-WAF-Blocked`, `CF-Ray` (Cloudflare), `Server: AkamaiGHost`
- Specific error pages — view source of a 403 and look for vendor logos/strings

## Fingerprinting at Scale

If you have many hosts:

```bash
# httpx — fast, concurrent, prints tech + status
httpx -silent -tech-detect -status-code -title -l hosts.txt
```

Output:

```
https://a.target.com [200] [Login] [Apache,PHP,WordPress]
https://b.target.com [403] [Forbidden] [Cloudflare]
https://c.target.com [200] [API] [nginx,Node.js]
```

Rapidly prioritizes — you can see at a glance which hosts are interesting.

## Version-to-Vuln Research

Once you've identified versions:

```bash
# searchsploit — local exploit-db
searchsploit apache 2.4.41
searchsploit wordpress 5.8
searchsploit nginx 1.14

# search online
google: "CVE WordPress 5.8"
```

Each version is a potential weak point. Even if nothing exploits directly, out-of-date software is often a sign of poor maintenance → more issues elsewhere.
